# 0023 多账号并行拉取与 Key 操作按钮放大

| 字段 | 内容 |
| --- | --- |
| 编号 | 0023 |
| 分支 | `feat/api-key-quota-adjust` |
| 状态 | 已完成 |
| 提出日期 | 2026-10-21 |

## 一、背景

账号状态刷新与展开账号后的 API Key 列表拉取原先都是串行执行。账号数量增加后，后面的账号
需要等待前面的账号完成，刷新体感明显变慢。

同时，Key 行悬浮后出现的复制、调额度、删除按钮尺寸偏小，点击面积和字号都不够舒适。

## 二、目标

多个账号并行拉取状态与 Key 列表，并放大 Key 操作按钮的点击面积和字号。

## 三、范围

**包含：**

* 账号状态刷新改为有界并行，结果仍按账号原顺序回传；
* 展开账号的 API Key 列表改为多账号并行拉取；
* 两类请求并发上限都设为 4，避免瞬间打满小实例；
* 单个账号状态刷新内部仍按 token 恢复链顺序执行；
* Key 行操作按钮字号从 9 提升到 10.5，并设置固定最小尺寸 64×26。

**不包含：**

* 不并行化 Heavy 用量曲线接口（继续单请求，避免触发限流）；
* 不修改登录与凭据恢复链；
* 不新增依赖。

## 四、完成点

* [x] `refresh.rs` 使用 scoped thread 与原子索引实现最多 4 个账号并行刷新；
* [x] 刷新结果按传入账号顺序回填，避免界面状态乱序；
* [x] `keys_rx` 从单请求改为按账号保存多个接收器，最多 4 个 Key 列表并行；
* [x] 失败的 Key 列表仍回退到本地缓存；
* [x] 放大 Key 操作按钮与字号；
* [x] 增加刷新并发上限测试。

## 五、验收标准

1. 操作：添加多个账号后手动刷新 → 预期：多个账号状态请求并行进行，整体完成时间明显短于逐个串行。
2. 操作：同时展开多个账号 → 预期：多个 Key 列表并行拉取，最多同时 4 个。
3. 操作：其中某个账号 Key 拉取失败 → 预期：该账号回退缓存，其他账号结果不受影响。
4. 操作：悬浮 Key → 预期：复制、调额度、删除按钮更易点击，字号更大。

**手工验证：**

* Windows：多账号展开与刷新，确认多个请求并行、按钮尺寸增大。

## 七、风险与回滚

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 并发过高触发实例限流 | 部分账号离线 | 并发上限固定为 4，不随账号数增长 |
| 并行完成顺序打乱界面 | 状态对应错误 | 刷新结果按原索引回填 |
| Key 列表并发写缓存冲突 | 缓存覆盖 | 每个账号独立处理结果并单独写自己的缓存 |

回滚方式：回退本功能对应提交。
