## 一、背景

展开账号只能看到"当前"的额度与近 5 小时用量，看不到**趋势**。网页后台能画
token 用量曲线，但那是浏览器里的图表库；托盘程序里再嵌一个 WebView 既重又违背轻量定位。

## 二、目标

展开账号后，在 Key 明细上方多一块"用量"区：切 **24 小时 / 7 天 / 30 天**，
用原生绘制显示 token 用量曲线，鼠标悬浮能看到该时间点的 token 与请求数。

## 三、协议（已用真实账号验证）

`GET /api/v1/usage/dashboard/trend?start_date=YYYY-MM-DD&end_date=YYYY-MM-DD&granularity=hour|day`

* 用户态接口（不是 admin 专属），数据范围就是**当前登录账号自己**；
* 响应 `data = { trend: [...], start_date, end_date, granularity }`；
* 每个点：`date`（小时粒度是 `2026-10-18 02:00`，天粒度是 `2026-10-18`）、
  `requests`、`input_tokens`、`output_tokens`、`cache_creation_tokens`、
  `cache_read_tokens`、`total_tokens`、`cost`、`actual_cost`；
* **只返回有数据的时间桶**（稀疏），缺口需要客户端补零。

## 四、设计

1. **数据层**（`api.rs`）：`UsagePoint { label, requests, total_tokens, actual_cost }`，
   `parse_usage_trend` 纯函数 + 单测；`HttpClient::usage_trend()`。
2. **状态**（`app.rs`）：`usage: HashMap<(账号 id, 区间), UsageSeries>` 缓存，
   `usage_rx` 单通道（同一时间只拉一个），TTL 60 秒；切换区间或重新展开才重拉。
3. **绘制**：`egui::Painter` 手绘——网格线、面积填充、折线、悬浮竖线 + 数值气泡。
   点数最多 31，纯绘制开销可忽略；不用图表库、不引依赖。
4. **指标**：主曲线 `total_tokens`；摘要行显示"合计 tokens / 请求数 / 实际花费"。
5. **区间**：24 小时（hour）、7 天（day）、30 天（day）。
6. **失败**：错误文案直接显示在用量区（不阻塞 Key 列表）；401/429 复用现有分类。

## 六、验收标准

1. 展开账号 → 预期：Key 明细上方出现"用量"区，默认 **24 小时**，有曲线或"暂无用量"。
2. 切到 7 天 / 30 天 → 预期：重新拉取并重绘，区间按钮高亮当前选中的那个。
3. 鼠标悬浮曲线 → 预期：出现竖线与该时间点的 token/请求数提示。
4. 断网 → 预期：用量区显示错误文案，Key 明细与复制功能不受影响。
5. `cargo test` → 预期：解析用例通过（含稀疏点与空数组）。

## 七、风险

| 风险 | 应对 |
| --- | --- |
| 接口是 Heavy 限流 | 只在展开/切区间/超过 60 秒时请求，且全局串行 |
| 时间桶稀疏导致曲线跳动 | 按服务端返回的点等距绘制，摘要用真实合计 |
| 30 天数据点较多 | 最多 31 点，无性能问题 |

## 八、结果

* 完成日期：2026-10-18
* 分支：`feat/usage-chart`

### 验证记录

* `cargo fmt --check` / `clippy -D warnings` / `cargo test`（**94 passed**）/ `build` 全绿；
* **真实接口实测**（需求方账号）：
  `GET /api/v1/usage/dashboard/trend?start_date=2026-10-17&end_date=2026-10-18&granularity=hour`
  → 返回 1 个桶（`2026-10-18 02:00`，1660 tokens / 1 次请求），确认是**用户态接口**、
  只返回有数据的桶；
* **实机截图**：展开账号后"用量"区出现，24 小时选中、曲线区有网格与数据点，
  摘要为 `合计 1.7k tokens · 1 次请求 · $0.027`；
* **区间切换**：点击「7 天」后按钮高亮切换、重新拉取并重绘（截图 `target/usage-7d.png`）。

### 与计划的偏差

1. 曲线按**返回点数等距绘制**，没有按真实时间轴补零：接口是稀疏返回，
   若补零需要按区间推 24/7/30 个桶并按 `date` 对齐，收益不大且容易被时区边界坑，
   先按"有多少点画多少点"实现；
2. 只有一个数据点时画成一个圆点（退化为点图），没有画"仅一个时间点"的提示；
3. 失败时把 `fetched_at` 也置为当前时间，避免每帧重试把 Heavy 限流接口打爆。

### 遗留问题

* 未按真实时间轴补零（见偏差 1）；
* 未做"按模型/Key 拆分堆叠"（网页有，托盘里价值较低）；
* macOS 未实机验证。
