## 一、背景

0011 已经能从用户态接口拉到当前登录账号自己的历史用量，但服务端只返回有数据的时间桶。
现有实现把这些稀疏点按数组下标等距绘制，导致历史时间轴被压缩，用户看不出用量在什么时候发生。

## 二、目标

展开账号后，用户能看到按真实时间桶排列、缺口补零的本人历史用量曲线，并能切换时间区间查看趋势。

## 三、范围

包含：

* 解析用量接口返回的 start_date、end_date、granularity；
* 把稀疏时间桶扩展成完整时间轴，缺失桶补零；
* 曲线按补零后的完整时间桶绘制，增加起止时间标签；
* 补充解析与补零的纯逻辑单测。

不包含：

* 不做按模型 / API Key 的堆叠曲线；
* 不在本地落盘保存用量历史；
* 不引入图表库或 WebView；
* 不调整用量接口协议。

* [x] README / AGENTS 登记改动

## 五、验收标准

1. 展开账号 -> 预期：用量区显示「我的用量」，默认 24 小时，曲线横轴有起止时间。
2. 服务端返回两个相隔多个小时/天的桶 -> 预期：中间缺口以 0 值连成时间轴，不再等距压缩。
3. 切到 7 天 / 30 天 -> 预期：按钮高亮、重新按对应粒度拉取并绘制。
4. 鼠标悬浮曲线 -> 预期：提示中的时间标签与真实时间桶一致，显示 token 和请求数。
5. 接口返回空数组 -> 预期：显示「该区间暂无用量」，不出现错误或崩溃。
6. 断网 -> 预期：用量区显示错误文案，Key 列表与复制功能不受影响。

## 七、风险与回滚

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 服务端时区与本地 UTC 日期边界不一致 | 首尾桶可能多一个或少一个 | 优先使用响应里的 start_date/end_date；日期解析失败时退化为原始点 |
| 接口不返回范围字段 | 无法补零 | 保留原始稀疏点并按标签排序，不阻断展示 |
| 30 天小时粒度桶数量过大 | 绘制开销增加 | 只接受 hour/day，桶数设上限，超出上限回退原始点 |
| 重复时间桶 | 总量重复或曲线覆盖 | 按标签合并 requests/tokens/cost |

回滚方式：git revert 合并提交，或把 dev 回退到本功能合入前的提交。
